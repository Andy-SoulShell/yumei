# 手机双模式：Safari / Chrome 兼容性检查

本轮修复了软键盘识别遗漏、聊天上翻与内容增高竞争导致的回跳，并补充聊天和抽屉的滚动边界约束。标准与实验玻璃模式均检查；本机能够完成浏览器引擎验证，尚未完成 iPhone / Android 真机验收。

## 修复

| 问题                                                                                | 影响                                                                                      | 修改                                                                                                                 |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 项目启用 `interactive-widget=resizes-content`，原判断仅比较当前布局与视觉视口高度。 | Chrome 同时缩小两个视口时漏判键盘，非聊天页面底部导航仍占位置，部分键盘浮层规则没有启用。 | 保存输入前的布局高度，同时兼容视觉视口独立缩小；按宽度变化重置横竖屏基线，输入框切换期间保留关闭动画前的高度。       |
| 所有 input 都被视为键盘输入。                                                       | 复选框等控件获得焦点时，可能错误进入键盘模式。                                            | 排除复选框、滑块、文件选择等非文字输入；继续支持 textarea 和可编辑内容。                                             |
| 用户上翻与回复增高同帧发生时，布局检测会忽略滚动事件。                              | 仍被判定停在最新消息，ResizeObserver 随即拉回末尾，打断历史阅读。                         | 用被动触摸和滚轮监听提前记录上翻意图；触摸结束后保留阅读状态，实际回到末尾后恢复跟随。轻触抖动和捏合缩放不解除跟随。 |
| ResizeObserver 即使已在末尾，也反复写入 scrollTop。                                 | 增加干扰浏览器原生滚动的机会。                                                            | 仅在末尾确有超过 1px 的偏差时调整；手指上翻后不再自动定位。                                                          |
| 只有页面主容器限制滚动穿透。                                                        | 聊天消息区与抽屉自身到达边界时，缺少明确的滚动链约束。                                    | 在实际聊天视口和通用 ScrollArea 视口设置 `overscroll-behavior-y: contain`，保留浏览器原生触摸滚动与缩放。            |

Chrome 对 `resizes-content` 的定义是同时调整布局和视觉视口，见 [Chrome 视口与软键盘说明](https://developer.chrome.com/blog/viewport-resize-behavior/)。页面现改用 `resizes-visual`，让支持该选项的 Chrome 与 Safari 采用一致的视觉视口补偿路径，避免键盘展开和旋转重复改变布局。高度基线作为仍缩小布局视口的触摸设备浏览器的兼容处理；普通桌面窗口调整不启用这一判断。现有 Safari 视觉视口顶部偏移补偿、16px 输入字号、键盘关闭恢复、玻璃退层规则继续保留。

## 检查环境与方法

- 隔离应用 `127.0.0.2:3100`、专用测试数据库与合成账号；上游协议验收 19 项通过。没有向真实用户发送消息。
- Windows Playwright WebKit 26.5 和本机 Google Chrome 155；390 × 844px、触摸/手机视口模拟、DPR 2；另检查 844 × 390px 横屏。
- 在实际聊天页面提供 500 条合成历史记录，检查标准 / 实验两种模式。键盘通过真实窗口尺寸调整及受控 VisualViewport 指标分别覆盖两种行为，不把模拟当作真实系统键盘。
- 浏览器默认代理字符串仍标识宿主浏览器，未靠修改代理字符串宣称运行了 iOS / Android。

## 结果

最终 78 项交互断言通过，两个引擎最终运行均未记录页面脚本异常：

- 500 条历史首次进入定位末尾；视觉视口 460px / 顶部偏移 80px 时，输入区底部位于 540px；继续变为 400px / 偏移 110px 后，历史阅读位置保持不变。
- 布局与视觉视口同时从 844px 缩至 480px 后，键盘标识生效；恢复窗口后清除临时高度并保留草稿。设置页实际密码输入框也验证底部导航隐藏。
- 70px 的工具栏变化、捏合缩放指标、键盘关闭时横竖屏切换未误触发；横屏从 390px 缩到 210px 时输入区仍贴住可见底部。视觉视口键盘已打开时再旋转，输入区也保持在可见底部。
- 触摸 / 滚轮上翻与内容增高同帧发生时不回跳，事件未被取消；回到底部后恢复跟随。
- 两层菜单留在视口内；实验模式仅子菜单保留模糊，父菜单退为实色。打开玻璃抽屉时后方导航退层。浅色 / 深色以及提高对比度后的实色退化路径均检查。
- 在历史上方增高 250px 后，两引擎原生滚动锚定均将 scrollTop 补偿 250px，可见消息顶部偏移保持不变。此结果不代表更旧 Safari 版本也具备同样能力。

另用 Chromium 协议触摸事件检查两种模式：长聊天在内容每 80ms 增高期间实际向上拖动超过 280px，未出现反向回跳；抽屉实际滚动 390px，后方聊天位移为 0。重复运行中部分手势没有触发松手后的续滑，部分观测到超过 500px 的续滑，观测期间均未回跳。这验证的是模拟输入下的浏览器路径，不能替代真机惯性与弹性回弹验收。

全量测试 120 个文件、1077 项通过；修改后键盘与滚动专项 20 项通过。TypeScript、修改文件 ESLint / Prettier、差异空白检查和生产构建通过。构建仍有原有的主分块体积及第三方纯函数注释提示。

## 玻璃与真机验证边界

Windows WebKit 中，`backdrop-filter` 和 `-webkit-backdrop-filter` 均报告支持，但截图没有呈现背景模糊。独立的静态最小页面、直接写入 `blur(20px)` 以及强制合成的对照仍是相同结果；Chromium 对照能正常模糊。因此该环境只用于布局、样式规则和浮层层级检查，不能据此通过或否定 iPhone Safari 的玻璃视觉效果。

该 WebKit 端口也报告不支持 `overscroll-behavior-y`，检查的是已有 body 滚动锁定退化路径；Chrome 则实际应用了 `contain`。iOS 自身的弹性回弹、系统键盘与候选栏、浏览器工具栏动画、真实背景模糊和合成器性能仍需真机确认。[Playwright 浏览器说明](https://playwright.dev/docs/browsers)区分其 WebKit 构建与正式 Safari，并说明不同宿主平台存在差异。

没有添加全局 `preventDefault` 或强制 GPU 合成规避，也没有添加旧的 `-webkit-overflow-scrolling: touch`。WebKit 已从 iOS 13 为溢出区域自动提供加速滚动，见 [WebKit Safari 13 说明](https://webkit.org/blog/9674/new-webkit-features-in-safari-13/)。目前的处理保留原生手势，减少程序滚动与手势竞争。
