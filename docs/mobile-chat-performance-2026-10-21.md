# 手机双模式：长聊天与玻璃叠加性能

本轮确认了长记录更新时的主线程卡顿，并通过消息行复用、稳定语音回调和减少输入框同步布局消除了测试中的连续长任务。实验玻璃保留现有材质与单层模糊规则。

## 测量方法

- 使用隔离应用、专用测试数据库和合成账号；上游协议验收 19 项通过。
- Windows Edge / Chromium，390 × 844px 触摸设备模拟、DPR 2、4 倍 CPU 降速。性能测量期间不并行运行构建或测试套件。
- 通过明确的列表夹具向实际聊天页面提供 50 / 500 条记录，模拟已经加载的长历史。分别在标准、实验模式运行 3 次。
- 长聊天场景：消息区受控滚动 6500px，同时输入固定文字序列；确认实际滚动位移。采集 `requestAnimationFrame` 间隔、Long Tasks 与浏览器主线程指标。
- 玻璃组合场景：500 条历史记录，受控流式快照每 120ms 更新一次，在此期间滚动实际亲密度抽屉 390px。消息和抽屉均使用产品组件，流式事件由浏览器夹具提供。
- 优化前基线为 `300d3af` 对应的生产前端资产；玻璃组合场景使用保留的该版本产物重新测量。初期没有实际位移的合成触摸手势尝试不计入玻璃滚动结果。

表格中的帧间隔为“3 次运行各自的 P95”的中位数。长任务采用浏览器 Long Tasks 的 50ms 门槛。

## 结果

| 场景                           | 模式     | 优化前 P95 | 优化后 P95 | 优化前长任务中位数 | 优化后长任务中位数 |
| ------------------------------ | -------- | ---------: | ---------: | -----------------: | -----------------: |
| 500 条记录：滚动并输入         | 标准     |     83.4ms |     16.8ms |                 44 |                  0 |
| 500 条记录：滚动并输入         | 实验玻璃 |     83.4ms |     16.8ms |                 44 |                  0 |
| 500 条记录：流式更新时滚动抽屉 | 标准     |    100.1ms |     16.8ms |                 18 |                  0 |
| 500 条记录：流式更新时滚动抽屉 | 实验玻璃 |    100.0ms |     16.8ms |                 18 |                  0 |

500 条记录的输入场景中，脚本执行时间中位数从标准模式 3506ms 降至 848ms，实验模式从 3115ms 降至 840ms，分别减少约 76% 和 73%。最终标准模式首次运行仍记录到一次 51ms 长任务，后两次为 0；实验模式三次均为 0。50 条记录也完成相同检查，优化后两种模式均无长任务。

抽屉单独滚动的 P95 约 16.8ms。实验模式打开抽屉后，后方聊天导航停止模糊，抽屉保留 `20px` 模糊与 `1.35` 饱和度。组合场景的改善来自减少后台聊天的重复工作，未降低玻璃效果。

另用 200 条记录、20 张不同 URL 的聊天照片检查首屏：两种模式均从请求 20 张降至 3 张，消息区仍贴住末尾。随后滚到更早照片，验证图片加载、原图查看及关闭后焦点返回。

## 问题与落地修复

没有发现 P0 问题。本轮处理了以下问题：

| 优先级 | 现象与影响                                                           | 原因                                                                             | 修改                                                                                                      |
| ------ | -------------------------------------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| P1     | 每次输入或流式更新都重复渲染数百条消息，主线程出现连续长任务。       | 历史消息直接在页面更新中展开；语音回调依赖每次变化的 mutation 对象，破坏行复用。 | 提取 `ChatMessage` 并按消息复用；使用稳定的语音 mutation 方法和播放回调；只传递头像与角色名等实际显示值。 |
| P1     | 字符追加期间，输入区重复强制同步布局，实验模式仍有较长帧。           | 每个字符都先将 textarea 高度清零，再读取完整高度。                               | 追加文字未溢出时保持高度；换行时扩展；删除、替换与宽度变化时重新测量，保留缩回行为。                      |
| P1     | 长聊天进入页面时集中请求与解码历史照片。                             | 聊天照片立即加载，解码策略未指定。                                               | 聊天照片使用 `loading="lazy"`、`decoding="async"`，在接近可见区域时加载。                                 |
| P2     | 新照片加入列表时，已有图片消息也会更新；原图选择可能随前插照片改变。 | 打开原图的回调依赖整个照片列表，预览按数组下标保存状态。                         | 固定打开回调，按照片 ID 保存预览状态，再映射当前下标。                                                    |

主要文件：`client/src/features/chat/ChatMessage.tsx`、`ChatMessages.tsx`、`useChatController.tsx`，以及 `client/src/hooks/useTTS.ts`、`useAutosizeTextarea.ts`。

## 验证与证据

- 新增回归覆盖：无关更新复用历史行、仅更新收到片段的消息、语音回调更新、照片前插后的预览定位、连续输入 / 换行 / 删除，以及语速修改后的实际配置。
- 手机输入区额外检查标准 / 实验 × 320 / 390px：12 行草稿、视觉视口高度 400px / 顶部偏移 80px、继续追加、缩回短文字、横屏最大高度，4 组通过。
- 全量测试 120 个文件、1068 项通过；TypeScript、修改文件 ESLint / Prettier、差异空白检查与生产构建通过。构建仍保留原有主分块体积提示。
- 本地证据目录：`output/mobile-performance-2026-10-21/`。500 条记录的最终输入对比为 `baseline-isolated.json` / `optimized-final.json`；另有 `optimized.json` 的 50 条记录、`baseline-glass.json`、`baseline-glass-stream.json` / `optimized-glass-stream.json`、`final-check-glass-stream.json`、`photos.json`、`autosize-regression.json`。全量测试结果为 `tmp/mobile-performance-tests.json`。测试资料与账号信息按仓库规则忽略。

这些结果用于比较同一环境下的主线程开销和卡顿趋势。触摸模拟、CPU 降速与受控滚动不能替代 iPhone / Android 真机的合成器、惯性滚动、温升和耗电测量；本轮不据此声称所有手机都能稳定达到某一帧率。
